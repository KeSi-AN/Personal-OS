# Architecture Decision Log

Each entry has a status (Proposed, Accepted, Superseded) and a short rationale. ADR-001 to ADR-015 were accepted with the design on 2026-11-02.

| # | Decision | Status | Why |
|---|---|---|---|
| ADR-001 | Single daemon process, asyncio, observers as supervised in-process tasks | Accepted | Fits the 300 MB budget and is simple to debug. Python exceptions are isolated per observer by the supervisor. Per-observer subprocess isolation stays as a config flag if a native crash ever happens. |
| ADR-002 | Daemon runs at logon in the user session through Task Scheduler, not as a Windows service | Superseded by ADR-024 | Services live in session 0 and can't see foreground windows, idle time, or lock events. (Task Scheduler turned out to need admin rights for a logon trigger.) |
| ADR-003 | Browser → daemon over native messaging; everything else over token-authenticated HTTP on 127.0.0.1 | Accepted | Native messaging pins the extension ID and opens no port to web pages. The CLI, editor extension, and dashboard need an API anyway. Host and Origin checks block DNS rebinding and web-page access. |
| ADR-004 | Shell hooks always append to a per-shell spool file, which the daemon tails | Accepted | Prompt latency can't depend on the daemon. Appending to a file is around a millisecond and can't hang. One delivery path covers both "daemon up" and "daemon down". |
| ADR-005 | git CLI (porcelain v2, `--no-optional-locks`) instead of GitPython | Accepted | Stable output contract, one less dependency, and it never competes with the user's git for `index.lock`. |
| ADR-006 | `ctypes` instead of `pywin32` for Win32 calls | Accepted | About 10 API functions are needed. Avoids a large dependency with a post-install step. |
| ADR-007 | Interval events are upserted by id, checkpointed every 60 s | Accepted | A crash loses at most 60 s of an open interval. One table holds both open and closed intervals. |
| ADR-008 | Privacy filter is a single choke point that fails closed | Accepted | A filter bug may lose data but can never leak it. |
| ADR-009 | Plain SQL migrations tracked with `PRAGMA user_version`; no ORM | Accepted | SQLite-specific features (FTS5, vec0, upserts, triggers) are easier in SQL. Fewer dependencies. |
| ADR-010 | CPython 3.12 managed by `uv` | Accepted | Widest wheel availability for later phases (voice/ML). 3.12.11 is already installed through uv. |
| ADR-011 | `forget` tombstones action-audit arguments instead of deleting the rows | Accepted | Keeps the audit log append-only (who did what, when) while still removing captured content from the forgotten window. |
| ADR-012 | Own UUIDv7 implementation for event ids | Accepted | Time-sortable ids with no dependency. The stdlib only gets `uuid7` in 3.14. |
| ADR-013 | No file shadow copies; diff summaries come from git numstat, or line/size deltas outside git | Accepted | Storing copies of your files would contradict "context, not logs" and enlarge the privacy surface. |
| ADR-014 | LLM background jobs gated on AC power + user idle + no full-screen app | Accepted | Laptop with a 4 GB GPU. Summaries mustn't drain the battery or slow down active work or games. |
| ADR-015 | Default data dir `%LOCALAPPDATA%\PersonalOS` on C:, outside Documents and OneDrive | Accepted | User-private ACL, not synced to the cloud, and never inside a watched root. Confirmed by your answer to Q8. |
| ADR-016 | Qwen only: `qwen3:4b` for fast and reasoning roles, `qwen3-embedding:0.6b` for embeddings | Accepted | Your answer to Q7. One chat model means nothing else competes for the 4 GB of VRAM. |
| ADR-017 | Tier 0–1 actions auto-run only for direct user requests; proactive or content-derived calls still confirm | Accepted | Your answer to Q5 (allow Tier 1), combined with the brief's rule that observed content must never trigger tools. |
| ADR-018 | Phone access through a separate, opt-in LAN listener (HTTPS, per-device pairing, limited routes); the core API stays on loopback | Accepted | Your answer to Q4. Keeps ingest and control off the network, and lets one phone be revoked without touching the rest. |
| ADR-019 | Google Calendar and Gmail as the first cloud integrations, opt-in, read-only scopes first, tokens in Windows Credential Manager | Accepted | Your answer to Q6. These are the first cloud calls, so they're explicit and minimal. |
| ADR-020 | Simulator scenarios written in TOML | Accepted | `tomllib` is in the stdlib, so no YAML dependency. |
| ADR-021 | Timestamps stored as integer Unix milliseconds (UTC) plus `tz_offset_min` | Accepted | Cheap comparisons and range indexes. No string-format ambiguity. Local-day queries use the stored offset. |
| ADR-022 | Migration 0001 creates only the tables phase 0 uses; later tables come in their own migrations | Accepted | No empty speculative schema, and the migration path gets exercised from phase 1 on. |
| ADR-023 | FTS5 tables use the `secure-delete` option, alongside `PRAGMA secure_delete=ON` | Accepted | `forget` must not leave deleted text in the full-text index or in free pages. Verified by a test that scans the database file bytes. |
| ADR-024 | Start at logon from the per-user Startup folder (a small `.vbs`), with a launcher process that restarts the daemon with backoff if it crashes | Accepted | Creating a Task Scheduler task with a logon trigger needs administrator rights. The Startup folder doesn't, and you can see and remove the entry like any other startup app. The launcher brings back the restart-on-failure Task Scheduler would have given. |
| ADR-025 | The CLI controls the daemon through the database (pause setting, `meta.forget` markers, a stop-request file); the local HTTP API moves to phase 2 | Accepted | Phase 1 has no browser or editor client yet, so an API would only add a port and an attack surface. The daemon polls these every second, which is cheap and keeps working when the daemon is down (the CLI still pauses and forgets). |
| ADR-026 | In a git repo, a file change's `lines_added`/`lines_removed` are the uncommitted totals against HEAD after that save; outside git they are the change since the last save the daemon saw | Accepted | git already knows the true diff, and no copy of your files is kept (ADR-013). Per-save deltas would need a copy of the previous version. |
| ADR-027 | The bash hook adds `ignorespace` to HISTCONTROL if it's missing | Accepted | The "space-prefixed commands are private" convention depends on it. Without it, bash would put the line in history and the hook couldn't tell it was meant to be private. |
| ADR-028 | Pausing ends every open interval at the pause time. After a forget, the daemon purges its queue, resets observers' open intervals, repeats the delete once, and drops late events in that window for 24 h | Accepted | Without this, an interval that was open when you paused or forgot would be written back by its next checkpoint, or by a spooled command that arrived late. |
| ADR-029 | The native messaging host appends to `spool/browser/` (like the shell hooks) instead of relaying to a local HTTP API | Accepted | No network port, no token, works while the daemon is down, and reuses the tested spool reader. The HTTP API stays unneeded until something has to *query* the daemon (phase 4 `ask`, phase 6 dashboard). |
| ADR-030 | The extension's ID is pinned with a public `key` in `manifest.json`; the host manifest's `allowed_origins` names only that ID | Accepted | An unpacked extension otherwise gets an ID derived from its folder path. With a fixed ID, no other extension can reach the host. The private half of the key was never stored. |
| ADR-031 | Enrichment (content type, search queries, GitHub/Stack Overflow/docs/YouTube details) runs in the daemon; the extension only sends the URL, a readable extract and two DOM hints | Accepted | Python is testable with recorded fixtures, the extension stays small, and enrichment rules can change without reloading the extension. |
| ADR-032 | Incognito is excluded three times: the manifest says `incognito: "not_allowed"` (it can't even be enabled there), the worker skips incognito tabs, and the host and the privacy filter drop anything flagged incognito | Accepted | Private windows are a hard exclusion in the brief. |
| ADR-033 | A page visit's active time comes from the window record (a Chrome/Brave/Edge window showing that page's title was in front, and you weren't idle), with the extension's own figure as a fallback | Accepted | On Windows, Chrome sometimes reports "no window focused" (address-bar dropdown, Chrome popups) and never reports focus coming back, so the extension's clock both over- and under-counted (100 s vs about 59 s; 11 s vs about 84 s in review). The window observer already knows exactly what was in front. Redacted titles are never matched, since they're ambiguous. The extension's figure is kept as `extension_active_ms`. |
| ADR-034 | Background processes (launcher, daemon, autostart) run under the base interpreter's `pythonw.exe` through `personal_os/boot.py`, with this project's site-packages put first on the path | Accepted | uv's venv `pythonw.exe` is a small launcher that starts a console `python.exe`, so the daemon opened a visible Windows Terminal window. Closing that window would have killed the daemon. |
| ADR-035 | If the privacy filter drops a newer version of an event that's already stored (an open visit that ends as a bounce, a page whose password field appears later), the stored row is deleted. Blocked events are counted once per id | Accepted | Otherwise an open checkpoint could outlive the decision to exclude the page, and re-sends inflated the blocked counters (13 for one tab). |
| ADR-036 | Every git repo seen becomes a project automatically (id = folder name, GitHub `owner/repo` from the remote with credentials stripped); manual projects and a built-in `none` ("not project work") sit alongside | Accepted | Repos are where the strongest signal (path) already is, so most events resolve with no setup. `none` lets corrections say "this is personal" instead of leaving it unassigned forever. |
| ADR-037 | The resolver takes the strongest signal's confidence, and only signals weaker than direct evidence (keyword, temporal, learned app rules) may combine, by noisy-OR, capped at 0.84 | Accepted | A path or repo match is near-certain and needs no help. Two weak signals that agree (a page's words and what you were doing around it) are real evidence together, but the cap keeps them below "confident" (0.85), so they still show in the inbox as guesses and never become anchors for other temporal decisions. |
| ADR-038 | Keyword matching is conservative: two or more matching words, each seen at least twice in the project; at least one word few projects share; the site's own name ignored; a 1.6× winning margin; only for pages and editor window titles | Accepted | On real data the first version filed Netflix and YouTube under a repo because of generic words ("home", "watch") and matched a login page by the word "login". A wrong confident guess is worse than an inbox item. Embeddings could join this signal later; phase 4 uses them for retrieval first (DESIGN.md §6.2). |
| ADR-039 | Assigning an inbox group learns a rule; assigning a single event doesn't unless you add `--learn`. A rule for a whole app starts weak (0.55) and strengthens as corrections agree | Accepted | One-off fixes ("this tab was for project X") shouldn't change how a whole site or app is treated. In evaluation, one correction of an AI-chat app over-learned and pulled every later use of it into one project. |
| ADR-040 | The inbox shows unassigned items and guesses below 0.7 that came only from keywords or timing; windows under 30 s and browser windows whose page visit is already listed are left out | Accepted | Those guesses are the ones most likely to be wrong (all ten cold-start mistakes were timing guesses), and listing them lets one correction fix them. Short and duplicate items would only bury the useful groups. |
| ADR-041 | Sessions come from one-minute buckets labelled by majority project; a 15-minute gap ends a session; runs shorter than 10 minutes are absorbed; rebuilt (not stored incrementally) every 5 minutes for the last day | Accepted | A short detour (a Stack Overflow page, a chat) doesn't split a coding session. Rebuilding from events means a correction or `forget` is reflected without a separate update path, and it's cheap at this scale (about 1,500 buckets a day). |
| ADR-042 | Acceptance is measured on day 2 of a labelled two-day scenario, after simulated inbox corrections on day 1, and on a hold-out day 2 written after tuning, by events and by time | Accepted | The brief's test is about a labelled day, and corrections are part of how the system is meant to work. A cold start can't know Netflix isn't work. The hold-out guards against tuning to the test; time-weighted accuracy guards against getting many short events right and the long ones wrong. |
| ADR-043 | Ollama is called with the standard library's HTTP client. `base_url` must be a loopback address. Every model layer is requested on the GPU, with a fallback to Ollama's own choice if loading fails. Thinking is opt-in (`ask --think`) | Accepted | No new dependency for a handful of JSON calls. A loopback-only URL means captured context can't be sent off the machine by a config change. Measured on the GTX 1650: Ollama's own estimate left `qwen3:4b` half on the CPU (7.5 tokens/s); all layers on the GPU gave 45 tokens/s in 3.8 GB at an 8k context. Thinking took about 60 s per answer. |
| ADR-044 | Embeddings are float32 rows in an ordinary table, searched by brute force (the first 512 of 1024 dimensions, renormalised). `sqlite-vec` isn't used | Accepted | A deleted row here is zeroed on disk by `secure_delete`, so `forget` and retention keep their guarantee. Triggers delete a vector with its event, extract or summary, or when an event becomes sensitive. At personal scale (thousands of items) brute force is fast enough. `sqlite-vec` would add a native extension whose deleted vectors aren't guaranteed to be overwritten. |
| ADR-045 | Background LLM jobs need AC power, 2 minutes idle, no full-screen app (Windows' own Focus Assist signal, `SHQueryUserNotificationState`) and capture not paused. They run in their own task and database connection, one item at a time, re-checking between items | Accepted | Refines ADR-014. A summary can take 20–50 s; it must never delay pause, forget or health, and must stop when you come back. The full-screen check caught a full-screen Brave video during development. |
| ADR-046 | Session summaries are written from a numbered evidence pack, never raw events. Every item must cite pack lines; uncited items are dropped; a summary with no grounded action is rejected (one retry, then stored as failed, at most 2 attempts per input). Each item stores the event ids it rests on. A session is summarised again only when its pack changes | Accepted | Grounding is checked by code, not trusted to the model. The pack keeps prompts small (about 4k tokens) and puts the privacy filter's output, not raw payloads, in front of the model. A 4B model echoed its instructions as the goal until the prompt carried a worked example and the task line came after the data; an echo check now rejects that. |
| ADR-047 | `ask` routes questions without the model (project, time range, intent), answers "I don't have data on that" without calling it when no evidence is found, and keeps only sentences that cite real evidence lines. Without a usable model it lists the facts it found. The model gets no tools | Accepted | Routing decides what evidence is collected, so it must be predictable and testable. Saying "no data" can't depend on a model's judgement when there's nothing to judge. With no tools, text planted in a page can at worst skew one answer, and every claim still shows its evidence. |
| ADR-048 | Phase 4 acceptance uses a fixed question set on a three-day labelled scenario. Routing and evidence are checked in the normal test run; the answers from `qwen3:4b` are checked in a separate run (`pytest -m llm`, or `personal-os sim eval-ask`) | Accepted | The brief's test is about correct, cited answers and saying "no data" when appropriate. Model runs take minutes and need Ollama, so they can't gate every test run, but the routing they depend on can. |
| ADR-049 | Actions are typed tools with a tier. The policy is a fixed table: tier 0 runs; tier 1 runs only when you asked directly and nothing captured has been read in that request; tier 2 asks every time; tier 3 is blocked and, when unlocked for a few minutes, still asks. The kill switch blocks everything | Accepted | It follows the brief and your answer to Q5 (allow tier 1), with ADR-017's limit that content-derived or proactive calls ask. A table is easy to test exhaustively and impossible for a model to argue with. |
| ADR-050 | "Taint": once a tier-0 lookup has put captured text in front of the planner, every later call in that request is content-derived (tier 1 asks, tier 3 blocked even if unlocked). A network call (`open_url`) whose arguments contain 40+ characters of what was read is blocked outright | Accepted | Prompt injection can only work through text the model reads. Tracking the request instead of trying to detect hostile text means a cleverly worded page can't talk its way past the check. |
| ADR-051 | The planner returns a JSON plan constrained by a schema (tool names from the registry, tiers 0–2 only), with thinking off; each call's arguments are validated against the tool before anything runs, with one retry showing the model what was wrong | Accepted | Ollama's native tool calling made `qwen3:4b` think first (5–42 s per request). A JSON plan took 1.3–3.4 s and chose the same tools. Tier 3 tools aren't even nameable by the model. |
| ADR-052 | The audit log is a table that SQLite triggers make append-only, with one row per stage of an action. The only permitted change is `forget` replacing arguments and details with a tombstone (ADR-011) | Accepted | An action log you can't trust isn't worth having. A row per stage (proposed, decided, started, finished, undone) records refusals and cancellations as well as successes. |
| ADR-053 | Undo is a recipe (`{tool, args}`) saved with the action and run through the same policy. Undo steps check that nothing changed since (file hash, commit still HEAD). `edit_file` keeps the original for 7 days in `undo/`, deleted by `forget` | Accepted | Undo must never destroy your later work, and it shouldn't be a back door around confirmation. Keeping one original per edit for a week is a narrow exception to ADR-013 (no shadow copies), made only for edits the assistant itself performed. |
| ADR-054 | The kill switch is a file in the runtime folder, set by `actions kill` or the daemon's Ctrl+Alt+Shift+K. Running tools poll it every 200 ms, and commands are killed | Accepted | Every process (CLI, daemon, a future overlay) sees a file at once, without a server. It also survives a crash: observe-only stays on until you explicitly resume. |
| ADR-055 | The dashboard runs inside the daemon (FastAPI on the daemon's event loop, 127.0.0.1 only) as server-rendered HTML with a little plain JavaScript; no build step and nothing loaded from the internet | Accepted | One process, no new runtime, nothing to download. Security doesn't depend on the page: each request needs the right Host (blocks DNS rebinding) and a session cookie from a one-time link (`personal-os dashboard` or the tray). Changes also need the X-POS header and a same-origin Origin (other websites can send neither). Pages set a strict CSP and refuse framing. |
| ADR-056 | Phone access is a second listener, off by default, on this laptop's private LAN address only (not 0.0.0.0), over HTTPS with a self-signed certificate made locally (`cryptography`). Pairing uses a 6-digit code (5 minutes, burnt after 5 wrong tries) that becomes a revocable device token stored as a hash. The phone gets read-only pages, ask, pause/resume and forget | Accepted | Your answer to Q4, with the design's limits: no actions, settings, exports or deletions from the phone. The firewall rule needs admin rights, so the page prints the exact command instead of changing system settings. There's no QR code, to avoid a dependency; you type the address and code. |
| ADR-057 | In the dashboard, an action that needs confirming becomes a pending card (Approve / Decline, laptop only, expires after 10 minutes); approving runs it again through the full policy | Accepted | A web request can't wait for a keyboard prompt. Re-running the policy on approval means a stale or tainted approval can't skip anything: tier 3 is still blocked, and the kill switch still wins. |
| ADR-058 | The tray runs on a thread in the daemon (`pystray`); the overlay is a separate `tkinter` process (stdlib). Hotkeys are Ctrl+Alt+Shift+P (pause), +K (kill switch) and +Space (overlay), and `doctor` reports one that another app has taken | Accepted | The tray must live as long as capture does. A crash in a window shouldn't touch capture, and tkinter needs its own main loop. Ctrl+Alt+Space was already taken on this laptop (likely by the Claude desktop app's quick entry), which a silent registration failure hid until `doctor` reported it. |
| ADR-059 | Memory facts are added only when you confirm them ("remember that …" shows the fact back first). They reach the model as "You told me: …" lines, are editable and deletable, and `forget` removes those created in its window | Accepted | The brief: long-term facts and preferences "I explicitly confirm", stored separately and editable. Nothing is ever inferred into memory from captured content. |
| ADR-060 | Rollups (a summary per day, a current-state note per project) are written by the gated background job from session summaries, commits, git state and key pages, grounded like session summaries | Accepted | The brief's project timeline (§5) and "where did I leave off" both need a short, current, cited picture of a project. Building it from summaries keeps prompts small, and grounding keeps it honest. |
| ADR-061 | Export writes JSON lines per table or Markdown per project (embeddings, device tokens and settings are never exported). Deleting a project removes its events (and so their text and vectors), sessions, summaries, rollups and rules, keeps the audit log, and archives the project | Accepted | The brief's export and per-project delete. Archiving stops the repo from being re-added as a project a minute later; the audit log stays because it records what the assistant did, not what you did. |
| ADR-062 | Settings that apply at start (sources, phone access) restart capture on request: the daemon exits with code 75 and the launcher starts it again at once | Accepted | "Everything controllable without the terminal" includes applying a change. A restart code keeps the launcher's crash backoff for real crashes. |
| ADR-063 | Voice runs in its own process, started and restarted by the daemon while `voice.enabled`. Speech is recognised with faster-whisper `small.en` on the CPU (int8, loaded on first use, freed after 10 idle minutes). Push-to-talk is Ctrl+Alt+Shift+V, ending at the first pause | Accepted | Speech models stay out of the daemon's 300 MB budget, and audio crashes can't touch capture. The GPU stays with `qwen3:4b`. Measured here: about 3.6 s per phrase whatever the threads or beam, so beam 1 and 6 threads are used. Audio stays in memory; only command text reaches the action log. |
| ADR-064 | The wake word is optional and toggled (tray, dashboard, `voice wake on/off`): openWakeWord with a "hey Donna" model you train once (docs/VOICE.md), scored locally 80 ms at a time | Accepted | Your choice of phrase. openWakeWord has no prebuilt model for it, and training needs Colab-scale resources, so the feature ships ready but waits for your model rather than silently substituting another phrase. |
| ADR-065 | Replies are spoken by the configured voice with local fallbacks: Speechify (opt-in, cloud), then Piper (local), then the Windows voice (built in). Speechify receives only the sentence being spoken, using your own API key kept in Windows Credential Manager | Accepted | You asked to use Speechify. Its API is a separate product from the Premium app. Sending spoken replies off the machine is the one exception to local-only, so it's opt-in, limited to what's spoken, and stated where you turn it on. A failure never loses a reply. |
| ADR-066 | Spoken confirmations: a step that needs confirming is read out in one sentence; only a clear yes (yes, confirm, go ahead…) with no "no" in it approves; silence or anything else declines. Tier 3 is never offered by voice | Accepted | The brief allows a spoken "confirm". Misrecognition must fail safe, so ambiguity is a no. |
| ADR-067 | Briefings are composed from stored facts (rollups, summaries, failing commands, reminders, Google), not written by the model. They're offered once a day each, the first time you're active after the set time, as a notification, speech and a dashboard card | Accepted | A briefing read aloud has no evidence panel, so it mustn't contain anything invented. Waiting until you're active avoids talking to an empty room. |
| ADR-068 | Google uses the installed-app loopback flow with PKCE, written with the standard library. Scopes are `calendar.readonly` and `gmail.metadata` (headers, never bodies), the refresh token is kept in Credential Manager, and nothing fetched is stored | Accepted | Least privilege for the first cloud calls (ADR-019). No Google client library is needed for a sign-in and three GET endpoints. |
| ADR-069 | The MCP server (`personal-os mcp`, stdio) is read-only: ask, search, sessions, project_state, list_projects. Plugins are Python files in `plugins/`, off until `actions.plugins_enabled`, can't replace built-in tools, are marked in the log, and tier 3 plugins stay blocked | Accepted | An outside agent is never "you asking directly", so it gets context, not actions. Plugins run code, so they're opt-in and constrained by the same policy as built-in tools. |
| ADR-070 | Dependencies are locked for Windows only (`[tool.uv] environments`), and `requires-python` is 3.12 | Accepted | openWakeWord's Linux dependency (`tflite-runtime`) has no Python 3.12 build, which broke resolution for every platform. Windows is the only platform with observers today; Linux and macOS come later (ROADMAP). |
| ADR-071 | The voice popup is a pywebview window (WebView2) in its own process, started by the voice process when a turn starts and closed a few seconds after the reply. It reads the runtime folder only (voice.json's `turn`, the pause and kill-switch markers), about 5 times a second. The page is an HTML string from the package with a strict CSP; the page's API can only read that view, pin, close and open the dashboard through the one-time login link | Accepted | Chosen over **Electron** (a second runtime of 100+ MB and a build step), **PySide6** (a 200+ MB Qt download for one small window) and **tkinter** (already used by the overlay, but no animation, poor text rendering and no way to share the dashboard's look). pywebview reuses WebView2, which Windows 11 ships, adds a few MB of Python packages, needs no build step, and costs nothing while closed: measured here at about 145 MB private memory and 1.7% CPU while open and animating, zero when closed (docs/BUDGET.md). Files instead of a socket keep it out of the voice process: a popup that is slow or crashes can't delay recording, and missing WebView2 just means no popup (doctor says why). |
| ADR-072 | Voice conversations: an answer to "Did you mean …?" is read as choose, correct, new request or cancel (rules first, the local model only for what they can't place), with at most two questions per turn. A "no, …" during a confirmation is an amendment, run as the next request. After a reply, voice listens for a follow-up for `followup_s` (6 s) without the hotkey; "thanks" or silence ends it. The last few exchanges are kept in memory for 5 minutes and given to the planner as context, without replies from `ask` | Accepted | Treating every non-yes as a no made Donna drop corrections ("I wanted Zoom") and amendments. Rules keep the common cases fast and testable; the model (about 0.8 s warm on qwen3:4b, 6 of 6 sample answers right) only reads your own words, so nothing is tainted, and it can't run anything itself. A follow-up is a normal turn: same policy, same confirmations. Leaving `ask` replies out of the planner's context keeps captured text away from actions (ADR-050). A real-time framework (LiveKit) was considered and set aside for now: the problem was dialogue handling, not audio transport, and everything runs on this laptop. |
| ADR-073 | A due reminder is shown in the popup (one file per alert in `runtime/alerts/`, kept until dismissed, 12 hours at most); the Windows toast is the fallback. Spoken announcements (reminders, briefings) are queued for the voice process (`runtime/say/`) and said between conversations; the daemon speaks only when voice isn't running | Accepted | Windows suppresses toast banners during full-screen apps, Do Not Disturb and quiet hours, so a reminder was heard but never seen. One file per alert means the daemon adding and the popup dismissing never overwrite each other. Queuing speech keeps one voice (the configured one), never talks over a conversation, and keeps the speech model out of the daemon. A briefing's alert carries only its title, so the popup still shows nothing captured. |
| ADR-074 | Requests are routed by one function for voice and the overlay: wake word and filler dropped, questions recognised before action verbs. Reminders are read by rules (`reminder_parse`: set, change, cancel), and a missing message or time is asked for, never filled in by the model. A planned call whose text comes from the earlier conversation rather than the request needs confirmation | Accepted | A real conversation went wrong in three ways with one root each: "Do I have any reminders?" was routed as an action because "do" was an action verb, and the planner then copied an earlier sentence into a new reminder and ran it as "asked for directly"; the model stored "Remind me in a minute" as the message when a pause cut the real one off; and there was no tool to change a reminder. Rules make reminders fast and testable, and the provenance check closes the path from context to action without blocking requests that use your own words. |
| ADR-075 | Donna is one agent loop over general tools, local on `qwen3:4b` (docs/AGENT.md). Each step's JSON starts with a decision ("answer" or "use_tools"); the rules and worked examples come after the tool list; repeated calls aren't run again; the last step can only answer; a `recall`-only step is passed through. New tier-0 tools: `now` (open windows, browser tabs, idle, reminders; live state, never stored), `recall` (the old `ask` as a tool), `list_reminders`, `remembered_facts`. Voice, the overlay and `personal-os chat` use it; the fast rules stay in front | Accepted | "Add a tool per request" didn't scale and fixed lanes couldn't converse. A 4B model fills a fixed form well and plans long chains poorly, so the loop is built around a forced first decision and a bounded, answer-only last step. Measured: general answers about 2 s, one-tool answers 3-6 s warm.
